# NBA Fantasy 长线规划：得分预测模型设计

> 状态：v1.0 · 已实现（2026-11-07）· 三期一次落地
> 目标：把「每日一阵」的六项预测骨架移植到 NBA Fantasy，让排阵容由**预测得分**驱动，而不是由「排满率」驱动。
>
> 实现与验证速览：
> - 预测引擎 `src/web/fantasy-projection.js`；数据构建 `src/fantasy-data.mjs`（线上接口与落盘脚本共用）
> - 优化器 `src/web/fantasy-model.js`：净得分目标 + 双模式 + 付费转会
> - 预测落盘 `data/fantasy/record-predictions.mjs`；loss / 校准 `data/fantasy/evaluate-predictions.mjs`
> - 实测（2026-11-07，21 个比赛日）：单场相关系数 **0.80**（验收线 0.55）、MAE 8.3 分、优化器耗时 1.6 s

## 1. 背景

当前 `src/web/fantasy-model.js` 的球员预测只有三个输入：官方场均分 `ppg`、官方近 30 天状态 `form`、两个弱对位系数。优化器的默认排序则是
`fullDays → fullSlots → budget → points`（`MODE_ORDER.coverage`），**得分排在最末**。结果是：模型在努力「每天凑满 5 人」，而不是「拿最高分」。

而 NBA Fantasy 的总得分就等于 Σ 每日首发的 5 人得分。排满本身不产生分数，只是得分的手段。因此需要两件事同时改：**预测更准**，**目标函数对齐**。

## 2. 计分口径（已验证）

官方 `bootstrap.game_config.scoring`：

```
{ points_scored: 10, rebounds: 10, assists: 20, blocks: 30, steals: 30 }
```

即每 1 分 10 分、每 1 篮板 10 分、每 1 助攻 20 分、每 1 盖帽/抢断 30 分；**不扣失误、无命中率项**。内部数值放大 10 倍显示时统一除以 10：

```
fantasy = PTS + 1.0·REB + 2.0·AST + 3.0·BLK + 3.0·STL
```

实测校验：Luka Dončić 累计 308 分 / 65 板 / 64 助 / 6 帽 / 14 断 →
`3080 + 650 + 1280 + 180 + 420 = 5610`，与官方 `total_points = 5610` 完全一致。

与每日一阵 `statScore()`（`src/model.mjs:342`）的差异：

| 项目 | 每日一阵 | NBA Fantasy | 处理 |
|---|---|---|---|
| PTS | ×1 | ×1.0 | 沿用 |
| REB | ×1.2 | ×1.0 | 改系数 |
| AST | ×1.5 | ×2.0 | 改系数（↑33%） |
| STL | ×3 | ×3.0 | 沿用 |
| BLK | ×3 | ×3.0 | 沿用 |
| TO | ×−1 | 不计 | **删项** |

结论：**同一套骨架，换权重表、去掉失误项即可**。

## 4. 预测模型设计

沿用每日一阵 `scorePlayer()` 的分层骨架，改为**分项级**预测。

### 4.1 结构

```
预计分钟 m̂  →  每分钟产出率 rate_s  →  分项期望  →  求和  →  修正链  →  最终预测
```

### 4.2 分项基准与收缩

对球员 p 的每个分项 s ∈ {pts, reb, ast, blk, stl, min}：

- 原始场均 `μ_s = Σ stat_s / n`，n 为有效场次（优先取逐场日志；无日志时用官方累计 ÷ 反推场次）
- 同位置先验 `π_s` = 同位置组（BC=1 / FC=2）内样本 ≥3 场球员的 `μ_s` 中位数
- 收缩：

```
μ̂_s = (n·μ_s + k·π_s) / (n + k),   k = 2
```

`k=2` 比每日一阵的 `k=1` 更保守，因为分项方差明显大于总分方差。新秀 / 无样本者直接取 `π_s`，并标记 `baselineSource = 'position-prior'`。

### 4.3 分钟预测与轮换风险

```
m_expected = clamp(m̂_min, 8, 40) × b2bFactor × injuryFactor × roleFactor
```

- `b2bFactor`：球队在前一自然日有比赛时取 0.95（由 `events[].games[].kickoff` 判定）
- `roleFactor`：`m̂_min < 18` 时按 `1 − (18 − m̂_min)/18 × 0.5` 下调（对齐每日一阵 `lowMinutesRatio`，但上限 50% 而非 100%，避免过度惩罚）
- 分项期望统一表达为率乘以分钟，保证分钟变化正确传导到五项：

```
rate_s = μ̂_s / m̂_min
proj   = Σ_s  w_s · rate_s · m_expected,   w = {pts:10, reb:10, ast:20, blk:30, stl:30}
```

### 4.4 近期加权

- `recentFantasy` = 最近 3 场的 Fantasy 分（用 §2 公式自算），按 `0.5^k` 指数衰减加权
- 无逐场日志时，用官方 `form` 替代
- 混合权重：

```
proj_base = 0.55 · proj_baseline + 0.45 · recentFantasy
```

0.45 与每日一阵常规赛口径一致。每日一阵在**有**逐场日志时固定 0.45，本模块同样按「有日志 / 无日志」两档处理：无日志时降至 0.30（此时 `recentFantasy` 来自官方 30 天 form，粒度更粗）。

### 4.5 对位修正（分项级，二期开启）

对位是这套模型里**唯一带前瞻信息**的因子（其余都是历史外推），值得给足权重。但现有两个系数是 BAO5 六项口径，跨口径直接套用会污染，所以采用「**先给足权重、再由回测收敛**」的策略，而不是拍脑袋压低。

**一期**（沿用现有两个系数，权重明确提高）：

| 因子 | 原权重 | 实际实现 | 说明 |
|---|---|---|---|
| 历史对阵（`historyByOpponent`，`matchupSignal`） | 20% | **10%** | 它仍是 BAO5 六项口径，且小样本容易虚高；权重压到 10% 只作补充 |
| 对手分项防守（`opponentDefense`） | 15%（单一口径） | **分项 λ** | 见下 |

**二期实际落法（比原稿更省事、更准）**：`data/position/defense_vs_position.json` 本身就带 `PTS/REB/AST/STL/BLK` **原始值**（不止排名），所以不必再用逐场日志反推分项防守，直接按「该队该位置组让出的场均 ÷ 全联盟同组场均」构造 ratio 即可：

```
ratio(team, group, s) = 该队该位置组让出的 s 均值 / 全联盟同组 s 均值    # clamp 到 [0.6, 1.5]
conf   = clamp(games / 20, 0.35, 1)
mult_s = 1 + λ_s · (ratio − 1) · conf
对位乘数 = Σ_s (w_s · 场均_s · mult_s) / Σ_s (w_s · 场均_s)   # 按产出加权汇总
对位乘数硬封顶 [0.75, 1.25]
```

| 分项 | λ |
|---|---|
| PTS | 0.18 |
| AST | 0.15 |
| REB | 0.12 |
| BLK | 0.10 |
| STL | 0.10 |

位置组：1 = Back Court（PG/SG），2 = Front Court（SF/PF/C）。

这样做的好处：分项对位是**按球员自己的产出结构加权**的 —— 助攻型后卫对「对手助攻抑制差」的球队加分，篮板型内线对「对手篮板让得多」的球队加分，而不是所有人共用同一个系数。

⚠️ 提高权重会放大过拟合风险。约束条件：回测中若某分项的 `λ` 在 [0, 2λ] 区间扫描后最优点落在边界，说明该分项「要么无用要么被低估」，需单独复核而非继续加码。

### 4.6 伤病与首发

- **官方状态（已实现）**：由硬筛改为软折扣。`status ∈ {i, s, u, n}` 或 `chance < 25` → 硬排除；其余按 `chance/100` 折算乘数（原先 `chance >= 100` 才可用，会误杀大量 75% 的主力）。`status = 'd'` 单独压到 0.25–0.6。
- **轮换风险（已实现）**：用**逐场分钟**判轮换，比「首发信号」更稳。场均分钟 < 18 时按 `1 − (18 − m)/18 × 0.5` 下调，最多砍一半。
- **首发信号 `st`（暂缓，原因见下）**：`data/bao5/injury/latest.json` 的 `available` 条目里**没有 `st` 字段**（2026-11-07 实测），`st` 只出现在直播页 HTML 的 `slot-injury` 里，且只对「当天」有效。规划窗口是 21 个比赛日，给第 2–21 天套一个「当天有没有首发信号」的折扣会系统性误杀。
  → 结论：**不做 `st` 折扣**，只用 `chance/100` 与分钟轮换风险。若日后接入逐日快照，再补 `event.dateET === snapshot.date` 的精确匹配分支。

### 4.7 校准（三期）

```
calib(group, tier) = median(actual / predicted)   # 用已结算 event 的样本外回测
proj_final = proj × clamp(calib, 0.7, 1.3)
```

`actual` 由 BAO5 逐场日志自算（该项逐场官方得分端点实测 404，不可用）。按位置组 × 使用率档位（top100 / 其余）分组，样本不足 30 场时退回全局中位数。

### 4.8 修正链汇总（实际实现）

```
proj_base = (1 − w) · Σ_s w_s · 场均_s · roleFactor   +   w · recentDecayWeighted
w = 有逐场日志 ? (games ≥ 4 ? 0.45 : 0.35) : (有官方 form ? 0.30 : 0)
roleFactor = 分钟 < 18 时按 1 − (18−m)/18 × 0.5 下调，下限 0.5

proj_event = proj_base
           × 对位乘数（分项 λ 加权 + 历史对阵 10%，封顶 [0.75, 1.25]）
           × b2b（前一日也比赛 → 0.95）
           × (chance/100)
           × calib（三期，clamp [0.7, 1.3]，按位置组 × 持有率档位）
```

`场均_s` 在服务端就完成**同位置组中位数收缩**（`k = 2`），前端拿到的已是收缩后的值，避免每个消费者各算一遍。

> 实现位置：`src/fantasy-data.mjs`（收缩、先验、对位 ratio）+ `src/web/fantasy-projection.js`（混合、修正链）。

## 5. 优化器改造

### 5.1 目标函数（一期，最高优先级）

**「缺一人但总分更高」确实存在，且当前排序会系统性排除它。**

单日内多一个首发不可能是负收益（每人得分 ≥ 0），所以「当天想排满」永远成立。但**阵容名额与预算是全局稀缺资源**，凑满某天的最优解与最大化总分的最优解不同：

> 同一个名额的两个候选：
> - 球员 A：场均 40 分，21 个比赛日中只有 8 天有比赛 → 该名额贡献 `8 × 40 = 320` 分，其余 13 天空缺
> - 球员 B：场均 15 分，20 天有比赛 → 该名额贡献 `20 × 15 = 300` 分
>
> A 比 B 高 20 分，代价是 13 天出现空位。**谁更优取决于分差与缺位天数的比值，必须交给优化器按真实数字算，不能预设「必须排满」。**

更直观的整案对比：

| 方案 | 排满天数 | 预计总分 |
|---|---|---|
| X | 18 / 21 | **2100** |
| Y | 21 / 21 | 2050 |

当前字典序 `fullDays` 在第一位 → 一定选 Y，白白丢掉 50 分。

因此两个模式都**必须把得分放进排序**，区别只在优先级：

```js
// 得分优先（默认）
score:   ['points', 'fullDays', 'budget', 'appearances']
// 稳健排满（可选）
steady:  ['fullDays', 'points', 'fullSlots', 'budget']   // 得分提到第二位，不再排在 budget 之后
```

稳健模式保留「宁可少赚，也要每天有人上」的偏好（适合对预测信心不足时），但即便在稳健模式下，同排满率下也按得分决胜——这正是原先 `['fullDays','fullSlots','budget','points']` 缺失的一环。按你的口径，稳健模式即「**尽量排满**」，其定义就是 `fullDays` 第一位，不做进一步妥协。

### 5.1.2 优化目标 = 净得分（实测：付费转会扣 100 分）

实测证据（扫描 event 16 的 150 支真实队伍，取 `entry_history`）：

| 队伍 | `event_transfers` | `event_transfers_cost` | `points` |
|---|---|---|---|
| 4 / 34 / 36 | 2 | **0** | 1070–1560 |
| 64 | 2 | **1000** | 1160 |
| 131 | 1 | **1000** | 490 |

结论：
1. **每次付费转会固定扣 1000 原始单位 = 100 分（显示口径），不累进**（team 64 两次转会只扣一次，说明另一次在免费额度内）
2. `entry_history.points` 是**扣分后净分**（team 131 若为扣分前则应 ≥1000，实际 490）
3. 免费额度按 **Gameweek** 分配（同日 2 次转会 cost=0 的队伍存在，排除「每 event 1 次」）；现有前端「每 GW 2 个」的假设与此一致，但存在 chip 干扰，标注为**经验规则**

因此优化目标不是「预测总分」，而是：

```
净得分 = Σ(每日首发预测分) − 100 × 付费转会次数
```

这直接影响三处：
- 方案排序键用**净得分**
- §5.1.1 的空位收益也用净得分比较
- 界面必须展示「预计总分 − 转会扣分 = 净得分」，否则用户看到的分数是虚的

⚠️ 现版本优化器**完全不支持付费转会**（`while (available > 0)` 循环，额度为 0 就停），等于默认「永远不扣分换人」。现实中这会在关键球员伤停时错失明显更好的选择，需在 §5.2 补上。

### 5.1.1 空位经济性（一期验收必测）

单日内补满永远不亏（第 5 人的分 ≥ 0），所以「空位换分」的收益**只能来自全局约束的重新分配**，必须整案对比，不能按单日算。

回测时对同一批候选、同一预算跑两个解并报告：

```
空位净收益 = 得分优先解净得分 − 强制排满解净得分
边际换分   = 空位净收益 ÷ 得分优先解的空位天数
```

判定标准：
- `空位净收益 > 0` 且解中含空位 → 目标函数正确工作，「用空位换分」确实划算
- `边际换分 < 2 分/天` → 收益太薄，稳健模式反而是更好的默认
- 若该次回测中「强制排满」始终更高 → 说明投影模型对高分球员的赛程覆盖估计偏乐观，需回到 §4.2 复核

**安全线**：某日首发 < 3 人时强制补人。官方每天首发 5 人，低于 3 人通常意味着数据异常（赛程缺失 / 球队缩写不匹配），而非真实机会。

### 5.2 换人判据（一期）

现状 `if (after.fullDays <= before.fullDays && after.slots <= before.slots) continue;`（`fantasy-model.js:296`）会否决「人数不变、换个更强的人」这类正确操作。

改为**净得分判据**，并按「有没有免费 FT」分两档：

```js
const pointsGain = after.points - before.points;
const cost      = available > 0 ? 0 : 100;        // 免费额度用完即付费，固定 100 分
if (pointsGain - cost < threshold(available)) continue;
```

| 情形 | 阈值 | 口径 |
|---|---|---|
| 有免费 FT（`available > 0`） | **1.5 分** | 代价只是消耗额度（期权价值） |
| 无免费 FT（付费） | **110 分** | 100 分固定成本 + 10 分安全边际（模型误差约 ±10%） |

**不再要求「换人后每天的首发人数都不下降」**——这条约束正是与 §5.1 冲突的根源：它会否决「牺牲某天 1 个空位、换取其余比赛日显著加分」的转会。唯一兜底是 §5.1.1 的「单日首发 < 3 人则强制补人」。

**付费转会决策（新增，当前完全缺失）**：`available` 归零后不要直接 `break`，而是继续评估候选，仅当 `pointsGain > 110` 时执行一次付费换人，并在方案里记 `penalty += 100`。这样在核心球员伤停时仍能给出「扣 100 分换人，净赚 X 分」的方案，而不是给出一个明显更差的阵容。

**稳健模式不付费**：稳健模式的定义是「尽量排满」，不是「不惜代价排满」。该模式下 `threshold(0) = ∞`，只允许用免费 FT。

`options.ftThreshold` 与 `options.paidTransferThreshold` 均可覆盖，回测时分别扫描 `0 / 1.0 / 1.5 / 2.5` 与 `100 / 110 / 125 / 150`。

⚠️ **必须同步改内部评估函数**。`weekCoverage()` 现在返回 `score = fullDays×1e6 + slots×1e4 + points`（`fantasy-model.js:231`），是换人搜索的实际排序键——只改外层 `MODE_ORDER` 而留着它，搜索仍会向「排满」收敛。改为：

```js
score = netPoints × 1e3 + fullDays × 1e1 + slots    // 净得分主导
```

量级取 `1e3` 保证「1 分的得分增益」不会被「1 个空位」压过，同时保留极小权重的 tie-break。`netPoints = points − penalty`。

### 5.3 候选池（一期）

`planDailyTransfers` 现在每队每位置只留 2 人（`fantasy-model.js:254`），会漏掉低身价高性价比球员。放宽到 4 人，并对入池排序键加入 `pointsPerCost`（预测分 ÷ 身价）作为次级键。

## 6. 数据契约变更

`/api/nba-fantasy` 的 `players[]` 新增字段（server 端聚合，worker 端只算不读文件）：

```js
{
  statAverages: { pts, reb, ast, blk, stl, minutes, games, source },  // 已收缩
  recentGames: [ { date, opp, pts, reb, ast, blk, stl, minutes } ],    // 最多 5 场，降序
  starterSignal: { confirmed, date, source } | null                    // 二期
}
```

## 12. 预测落盘与 loss 闭环

模型要好，必须能被证伪。每次生成的预测分都要留档，等真实得分出来再回头算账。

### 12.1 落盘：`data/fantasy/prediction-log.json`

脚本 `data/fantasy/record-predictions.mjs`，与 `/api/nba-fantasy` **共用同一份数据构建与投影逻辑**（`src/fantasy-data.mjs` + `src/web/fantasy-projection.js`），否则「记录下来的预测」和「界面上显示的预测」不是同一个模型，loss 就没有意义。

规则：

| 情形 | 行为 |
|---|---|
| 比赛日 deadline 未到 | 每轮覆盖为最新预测（用户当时看到的就是这一版） |
| deadline 已过 | **冻结**，此后任何重跑都不改写 |
| 预测值与上轮完全相同 | 不写盘（CI 每 5 分钟跑一次，否则会刷出一串空提交） |
| deadline 超过 75 天 | 清理 |

结构（名册单独存一份，避免 21 个比赛日重复写 592 人的球队信息）：

```jsonc
{
  "version": 1,
  "modelVersion": "2026.11.fantasy.1",
  "scoring": { "pts": 1, "reb": 1, "ast": 2, "blk": 3, "stl": 3 },
  "roster": { "257": { "t": "14", "g": 1, "c": "1629029", "s": 26.7, "n": "Luka Doncic" } },
  "events": {
    "17": {
      "deadline": "2026-11-06T23:30:00Z",
      "dates": ["2026-11-06"],
      "games": [{ "home": "14", "away": "29", "dateET": "2026-11-06" }],
      "predictedAt": "...", "modelVersion": "...",
      "players": { "257": 62.34 }
    }
  }
}
```

### 12.2 真值来源

官方**没有**逐球员逐场 Fantasy 得分端点（`event/{id}/points`、`element-summary/{id}` 实测 404；`team-picks` 的 `picks[]` 只有 `element/position/multiplier`，不含得分）。所以真值只能自算：

```
actual = PTS + 1.0·REB + 2.0·AST + 3.0·BLK + 3.0·STL
```

数据来自 `data/history-player/current-season-logs.json`（BAO5 逐场日志，周更），用 `code` 对齐，用 `event.games[].dateET` 把比赛日映射到日志日期。

三条硬规则：

1. **日志没刷新到那天，整场跳过**——绝不把「还没更新」当成「没上场 = 0 分」。判定：该日期有出场记录的球员数 ≥ 60。
2. **日志覆盖了那天，没记录 = DNP = 0 分**。这不是数据缺失，而是期望值的正确目标：`E[得分] = P(出场) × 出场时产出`。校准因子会自动吸收轮换球员的 DNP 率。
3. 只统计 `deadline` 已过的比赛日。

### 12.3 loss 与校准：`data/fantasy/evaluate-predictions.mjs`

输出 `calibration.json`（供预测链读取）与 `loss-history.json`（趋势留档）：

```jsonc
{
  "samples": 187, "events": 1,
  "mae": 8.345, "rmse": 10.596, "bias": -2.539, "corr": 0.7988,
  "global": 0.7688,
  "groups": { "1": { "all": 0.68, "top": null, "rest": 0.60 }, "2": { "all": 0.81, "top": null, "rest": 0.82 } },
  "byEvent": [{ "eventId": 999, "coverage": 1, "n": 187, "mae": 8.345 }]
}
```

- `corr` = 单场预测值与真实值相关系数，**验收线 0.55**（单场方差天然大，0.5+ 已属可用）
- `global` / `groups` = `median(actual / predicted)`，即校准因子；样本 < 80（分组 < 40）时返回 `null`，预测链自动退回 1.0
- 校准按「位置组 × 持有率档位（≥10% 为 top）」分层 —— 明星极少 DNP，替补 DNP 多，一刀切会系统性低估核心球员

## 13. Chip（野卡）规划与付费转会上限

> 状态：设计定稿 2026-11-07 · 覆盖 §11「暂不纳入」中的 chips 条目（这里只做 Wildcard，其余见 §13.7）

### 13.1 官方规则（2026-11-07 实测 + 官方 FAQ 核对）

`bootstrap.data.chips` 给出全部 chip 的窗口，`team-picks.data.active_chip` 给出某队某日实际打出的 chip 名称。

| chip 代码 | 官方名 | 效果 | 次数 | 是否保留阵容 |
|---|---|---|---|---|
| `wildcard` | Wildcard | 该 Gameday **所有转会免费**（含该日此前已做的） | **3 次/赛季**，三个不重叠窗口 | **保留** |
| `rich` | All-Star | 该 Gameday 无限免费转会 + 无限预算，**下个 deadline 恢复该日开头的阵容** | 1 次/赛季 | **不保留** |
| `phcapt` | Gameday Captain | 指定一人双倍得分 | 每 Gameweek 1 次 | 保留 |

野卡三个窗口（`chips` 原始数据）：

| 窗口 | event 区间 | 官方文字描述 |
|---|---|---|
| WC1 | 2 – 39 | 赛季开始 ~ GW7 Day 1 |
| WC2 | 40 – 103 | GW7 Day 2 ~ GW17 Day 5 |
| WC3 | 104 – 159 | GW17 Day 6 ~ 赛季结束 |

⚠️ `chips` 里三条 `wildcard` 的 `number` 都是 `1`，**不能**据此判断「只有一张」。`number` 是「该窗口内的第几张」，官方文字明确 3 次/赛季，以区间数为准。

**野卡与 All-Star 的关键区别**（决定建模方式）：

- 野卡 → 那个 Gameday 的转会免费，**换完的人留下**，等同于「一次免费重建整队」
- All-Star → 只租一个 Gameday，**下个 deadline 强制还原**，长期价值接近 0（除非正好撞上单日大爆发）

因此本模型只对**野卡**做主决策；All-Star 原记为「暂不建模」（见 §13.7），2026-11-07 修订后改为「只补缺口日」的受限建模。

### 13.2 顺带修正的三个基础错误

实测规则文本时发现三处与官方不一致，且都会影响野卡决策，必须一起修：

| # | 现状 | 官方规则 | 影响 |
|---|---|---|---|
| 1 | `banked = available` 把未用完的 FT 结转到下周 | 「unused free transactions **do not carry over**」，每周恒定 2 个 | 高估可用转会次数 → 低估野卡价值 |
| 2 | 账号模式下第一个比赛日被当成「免费建队日」，不消耗 FT | 第一 deadline（10-20）之后，任何转会都计入该 GW 的 2 个免费名额 | 少算 1–2 次转会成本 → 方案净得分虚高 |
| 3 🚨 | 把「**本周剩余** FT」当成**整段窗口**的固定配额（`availableAtStart = weeklyQuota` 对每周同一个值） | 本周用光只会锁住**本周**；下个 Gameweek 重新给 2 个 | 本周 FT=0 时后面三周一次免费换人都排不出来，等于把方案锁死 |

修正方式：

- `available` 每周重置、不读 `banked`；「免费建队日」只在**未绑定账号**（即真的在建队）时成立。
- 第 3 条：`weekOrdinal === 0 ? firstWeekQuota : perWeekQuota`。`firstWeekQuota` 由账号读出（`2 − 本周已用转会数`，`team-transfers` 按 `event` 过滤当周），之后每个 Gameweek 一律 `rules.freeTransfersPerWeek = 2`。
- 官方 `game_config.max_extra_free_transfers = 0` 是「不累积」的硬证据，写进注释防止后续改动又把它当成可累积资源。

### 13.3 野卡建模：枚举候选日 + 局部重建

野卡不是一个连续变量，而是一个**日期选择**。设规划窗口为 `events[0..n)`，野卡在 `d` 日开启：

```
总分(d) = Σ_{i<d} base.daily[i].points            # d 之前的规划不变
        − Σ_{i<d} 付费扣分
        + tail(d).points − tail(d).penalty        # 从 d 起重新规划
```

其中 `tail(d)` 的起手阵容是「在 d 日以剩余赛程最优的方式重建的 10 人」。因为 `planDailyTransfers` 本来就把「传入窗口的第一个比赛日」当作免费建队日，所以 `tail(d)` 天然满足「野卡日转会免费」的语义——**不需要为野卡写单独的交易逻辑**，只需要换掉起手阵容。

重建的搜索目标与主方案一致（`mode` 相同），评价窗口是 `d..end`（只看还剩多少比赛），预算口径见 §13.4。

```
最优野卡日 = argmax_d 总分(d)
建议开卡   ⟺ max_d 总分(d) − 总分(不开) ≥ wildcardThreshold
```

`wildcardThreshold` 默认 **20 分**（约合半名球员的单场产出）。理由：野卡是稀缺资源（3 次/赛季，而规划窗口只覆盖 3 周），换来的增益要大到值得「用掉一次机会」，否则应留到后半赛季阵容崩坏时再用。该参数可调，回测时扫 `0 / 20 / 40 / 60`。

### 13.4 野卡的预算口径（容易算错的地方）

野卡不是「白送 1000 万」，而是「免手续费卖光重买」。所以：

```
可支配资金 W = Σ 现有阵容的卖价(selling_price) + 银行余额
约束         = Σ 新阵容的买价(now_cost) ≤ W
```

三个必须注意的点：

1. **卖价 ≠ 当前身价**。官方 `element_sell_at_purchase_price = False`、`transfers_sell_on_fee = 0.5`，即卖价 = 买价 + 50% 的涨幅。用当前身价算 W 会系统性高估可支配资金。
2. **被锁定的球员按卖价计入**（不卖就不产生资金变化，但占用了等额资金）。
3. 重建后剩余资金 = `W − Σ新阵容买价`，必须正确传给后续的转会规划，否则之后的换人会因「银行算错」而全部被否。

实现上给 `optimize()` 增加 `lockedCosts`（id → 卖价）与显式 `budget = W`；锁定的球员在搜索中用覆盖后的成本参与预算检查。

### 13.5 候选日的选取

不必枚举全部 21 天——野卡的收益在**同一 Gameweek 内几乎单调**（越早开，覆盖的比赛日越多），所以候选集取：

1. 每个 Gameweek 的**第一个** Gameday
2. 规划窗口的**第一个**比赛日（若是周中，当天开卡也合法）
3. 以上都需落在**当前可用的野卡窗口**内（`start_event ≤ id ≤ stop_event`）

21 天窗口约产生 3 个候选，每个候选一次 `optimize` + 一次 `planDailyTransfers`，实测总耗时增加约 1.5–3 秒（在 Worker 里跑，不阻塞界面）。

### 13.6 付费转会次数上限（用户输入，按周计）

界面输入 **「每周扣分换人上限」**，默认 **2**，范围 0–5，语义是**每个 Gameweek**——与 FT 同样按周重置。理由：

- FT 每周重置、付费换人在官方也是每周独立行为，若上限做成「整段窗口累计」，窗口越长（21 天）扣分越失控，而用户真实决策是「这周要不要吃一次 −100」。
- 21 天窗口 × 每周 2 次 = 最多 6 次，旧版「整窗口上限 3」反而把后面的周饿死了。

判据不变：付费换人必须让**剩余赛程**的净增益 ≥ `paidThreshold = 110`（100 分固定成本 + 10 分安全边际）。所以实际付费次数通常远小于上限——上限只是「不许超」，不是「必须用」。

`MAX_PAID_TRANSFERS_PER_WEEK = 5` 保留为物理护栏（用户填 99 时也不至于把阵容拆烂）。

### 13.7 Chip 建模范围（2026-11-07 修订）

| chip | 决策 | 原因 |
|---|---|---|
| `wildcard` | **做**（用户勾选后规划开卡日） | 换完的人留下，一次免费重建整队，长期收益可算 |
| `rich`（All-Star） | **做，但只补缺口日** | 只租一个 Gameday 且强制还原，长期净收益接近 0。唯一明确正收益的场景就是「那天怎么排都缺人」，所以只在 `starters < 5` 的比赛日评估，最多看 3 天，取增益最大者；增益 < 20 分不动用（全季只有 1 次） |
| `phcapt`（Gameday Captain） | 不建模 | 双倍得分作用在**单场**，需要「谁最有爆发力」而非「谁期望最高」，属另一套模型 |

All-Star 的实现要点：

1. **租借 = 单日完全自由重建**：`optimize(players, [], [当天], {budget: W})`，`W = Σ现阵容卖价 + 银行`。
2. **只改当天**：写回 `daily[i].points / starters / full`，不动 `roster`、不动 `moneyBank`、不消耗 FT、不计入付费额度——因为官方语义就是「到下一个 deadline 自动还原」。
3. **周汇总同步**：补位后重算该周的 `fullDays / appearances`，否则逐日明细会和周汇总打架。
4. **缓存**：最优租借阵容只取决于 `(eventId, W)`，与当前阵容无关，按此键缓存复用（4 个模式共享，省掉 3/4 的搜索）。

## 14. 起算日、规划长度与「预估分标尺」

### 14.1 起算比赛日（`startEventId`）

用户本周 FT 用光时，真实诉求是「从下周开始怎么排」，而不是「从今天的比赛日开始」。所以窗口起点改为用户可选：

```js
const startId = Number.isFinite(Number(startEventId)) ? Number(startEventId) : data.currentEvent;
const events  = data.events.filter(e => Number(e.id) >= startId).slice(0, clamp(eventCount, 1, 21));
```

- 未绑定账号时窗口首日仍免 FT（在建队）；绑定账号后首日就要占用本周剩余 FT。
- `eventCount` 上限取「从起算日起剩余的比赛日数」，前端 `syncEventCount()` 会同步 `max`，避免传进空窗口。

### 14.2 预估分标尺（为什么 21 天 3000–4200 分是正常量级）

规划窗口的合计分是「N 个比赛日 × 每天 5 名首发 × 每场预测分」，单看绝对值无法判断高低，必须给锚点。`src/fantasy-data.mjs` 的 `buildBenchmarks()` 用**官方 fixtures 的逐场分项**（口径与游戏完全一致）算出：

```
已结算比赛日 → 每名球员当日实际幻想分（pts×1 + reb×1 + ast×2 + blk×3 + stl×3）
             → 当天最高的 5 人合计 = 「当日最佳 5 人」
benchmarks = { settledEvents, best5Average, best5Median, days[] }
```

界面在指标下方显示：本方案日均 X 分 / 实测日均 Y 分 = Z%。分母是「全联盟当天最赚的 5 个人」，而玩家只有 10 人阵容、每队限 2 人，Z 落在 55%–70% 才是合理的（2026-11-07 实测：模型全池最佳 5 人预估日均 285.7，实际均值 316.2，模型略偏保守）。

口径校验（同日实测，避免「模型把量级算错」这类误判）：

| 校验 | 结果 |
|---|---|
| 分项加权重算 vs 官方 `points_per_game` | 中位比值 **1.000**，误差 0.00（权重 `pts1/reb1/ast2/blk3/stl3` 全对） |
| 每个 event 的比赛场次 | 2–14 场，按 `fixture.event` 精确分区，无重复计入 |
| 单场最高实际分 | 65（`element.event_points` 前 20 名 ≥ 24），确认「每个 Gameday 独立计分、每天首发 5 人」 |
| 球员出场率（场均 ≥15 分钟者） | 中位 **1.000**、25 分位 0.875 ⇒ 无需额外「出场概率」折损 |
